# 系统日志检查（2026-10-30 晚）

对象：`dash`，内核 `6.6.143-4k #3`，init_boot A/B 已还原 OS4 官方。采样时间
04:53–04:56，开机约 8 分钟；日志快照在 `handoff/logs-20261030/`（本地证据，
不入库）。

## 1. 结论

- **没有致命问题**：无 kernel panic / BUG / 真实 Oops，无 KCFI/未知符号/
  vermagic/CRC 拒载，无当前 boot 的 `am_crash`/`am_anr`/lowmemorykiller，
  pstore 为空，crash buffer 没有 Java/native crash。
- **有一条真实 kernel WARN**：vendor `mtk_cmdq_drv_ext` 探测时重复注册
  `/proc/cmdq`，触发 `fs/proc/generic.c:398 WARN`；当前 `panic_on_warn=0`，
  display/camera/cmdq 通路正常，属于 vendor 调试接口注册失败。上一轮 6.6.143
  boot 的 dmesg 也有（4 处），stock 6.6.118 样本中没有；更像 6.6.143 procfs
  的重复名 WARN 把原有 vendor 问题显性化。
- **其余主要是厂商日志噪声和已知 ExtM/mmd 行为**；SELinux 保持 Enforcing，
  没有针对 F2FS/EROFS/ExtM/backing_dev 的 denial。
- 高 load average（~19）不是 CPU 忙：CPU 大部分 idle；18 个 D 状态任务是
  vendor 常驻内核线程（`wdtk-*`、`hang_detect`、`ccci_*`、`block2mtd_retry`
  等），另有开机后短时 swap 抖动。`MemAvailable≈8.9 GB`，`oom_kill=0`。

## 2. 内核日志（dmesg 74,322 行）

实际 WARN：

```text
fs/proc/generic.c:398 proc_register+0x178
  cmdq_proc_create+0x20 [mtk_cmdq_drv_ext]
  cmdq_probe ...
```

- 同一 boot 中 `WARNING: Unprivileged eBPF is enabled` 是安全加固提示；
  stock.config 与当前 config 都未设 `CONFIG_BPF_UNPRIV_DEFAULT_OFF`，
  `kernel.unprivileged_bpf_disabled=0`，不是本轮引入。
- `Call trace` 12 处全部来自 vendor：cmdq probe、`cam_fs` init 返回 1、
  Bluetooth/conninfra 固件下载等待；不是我们的 hook/ThinLTO/pid 代码。
- `block2mtd: error cannot open /dev/block/by-name/oops` 后正常重试并
  `mtdoops Attached`，是 pstore/oops 分区初始化顺序。
- `ExtM: Cannot change disksize`、mmd/swapon_all 的 mkswap 失败是已知冲突：
  ExtM 已先初始化 zram，AOSP mmd 后到；内存扩展/回写正常。
- `vold: open /sys/block/zram0/idle error:-1`：`idle` 是 write-only sysfs，
  vold 读失败不表示 ExtM 异常。
- 充电器每秒打印 `failed to get slave cp charger` / `failed to get load
  switch dev`：USB 供电和充电正常（`status=Charging`），是可选从充/load
  switch 探测失败的 vendor 噪声。
- Bluetooth 启动时 824 条 `btmtk ... tty write failed` 固件重试；BT 最终
  `State: ON`、`Bluetooth crashed 0 times`，属于下载重试噪声。

## 6. 建议

1. 若要消掉唯一的 kernel WARN：修 vendor cmdq 的重复 `proc_mkdir("cmdq")`
   （需要重编 vendor 模块）；当前不影响功能，暂不紧急。
2. 安全加固可考虑 `CONFIG_BPF_UNPRIV_DEFAULT_OFF=y` 或 sysctl=2，但这是
   偏离 stock 的行为，需 A/B/策略确认。
3. `mi_game.ko` 的 `__get_mi_task_struct` 每任务日志和 charger 每秒
   `failed to get slave cp charger` 会淹没 dmesg；这是 vendor 模块日志级别，
   查问题时先按关键字过滤。
